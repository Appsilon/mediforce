The Workflow

Every step, and who does it

Scripts, agents and people each take the part they're best at. Click the diagram to see it full size, or read the full write-up on the Appsilon blog.

The Challenge

You need realistic study data.
Asking a model for it falls over.

Synthetic data lets you test pipelines before real data arrives, train people, build validation rules and run demos without a data use agreement. Generating it with a model alone fails for reasons that compound.

Conformance is structural

SDTM has required variables, controlled terminology and relationships between domains. Plausible-looking output checks none of it, and data that fails CORE can't test anything CORE will later run against.

It has to be your study

A generic template with your study ID swapped in isn't a synthetic version of your trial. The arms, visits and schedule should match the protocol.

Generated output isn't reproducible

Ask twice and you get two different datasets. If you can't regenerate the exact data a test suite was validated against, it wasn't validated against anything in particular.

Building it by hand is slow

A programmer can build a realistic synthetic study, but it takes days, and it has to be redone for the next study.

How It Works

The model interprets. Code generates. A person checks the spec first.

The language model only does what needs interpretation. Everything that has to be reproducible runs as deterministic code.

Human

Enter an NCT ID

A ClinicalTrials.gov study ID is the whole input.

Script

Fetch the study record

A script calls the ClinicalTrials.gov API and saves the study's metadata. It takes seconds, and no model is involved.

Agent

Configure the study

An agent reads the protocol and turns it into a structured specification: which domains, visits and arms, and what the treatment schedule looks like.

Human

Review the configuration

A person checks and adjusts the specification before any data is generated.

Script

Generate and validate

The approved specification goes to synthsdtm, an open-source R package, with a fixed seed, and CDISC CORE checks the result. The same specification and seed give the same datasets every time.

Human

Review the output

The reviewer sees the generated domains, CORE findings, conformance results and downloadable reports, then approves or asks for changes.

Human Review

The gate sits before generation, where it does the most good.

The specification decides everything downstream. If the agent misreads the protocol and sets up the wrong arms or visits, every dataset comes out wrong in a way that's internally consistent and hard to spot. Checking the specification takes minutes; working out from 31 generated domains that it was wrong does not.

Earlier versions of the workflow had no review here. It was added once building the workflow showed where it was needed. Each version is kept and locked, so you can open two side by side and see exactly what changed.

Cost

About $2 a run, tracked per step.

A run generates 31 domains, including findings and trial design, for around $2 in model spend. Mediforce tracks that spend per run and per step, and because models are chosen per step, the expensive model only runs where interpretation happens. Fetching the record and generating the data never touch a model.

Controlled terminology is used when you supply a CDISC API key. CORE conformance checking is optional and on by default.
