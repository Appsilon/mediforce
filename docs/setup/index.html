Self-hosting

Run Mediforce on your own server

Mediforce is Apache-2.0 and runs entirely on infrastructure you control. There is no hosted tier to sign up for and nothing calls home. This page walks the whole path: what to get before you start, what the bootstrap does, and how to tell it worked.

Time
About 30 minutes
You need
A Linux box and a domain
Runs as
Five Docker containers

What you are about to run

A deployment is five containers behind a reverse proxy. Nothing else is required, and nothing is hosted by us.

platform-uiThe app itself: the workflow editor, the run views, the API.
container-workerRuns each workflow step in its own container, which is why a step's code cannot reach the host.
postgresEverything durable: workflows, runs, users, the audit trail.
redisThe run queue.
caddyTLS. It gets a certificate on first start, so nothing to buy or renew.

A sixth, migrate, runs the database migrations and exits. There is no manual migration step, on the first deploy or on any upgrade.

Before you start

Three things, and only the first two are needed to get to a login screen.

A serverUbuntu 22.04 or newer, 4 vCPU and 8 GB RAM, with ports 80 and 443 free. Agent steps build and run containers, so this is a working machine, not a bastion.
A domainAny name you can add a DNS record to. Caddy needs port 80 reachable from the internet to get its certificate.
An OpenRouter keyOnly if a workflow uses agent steps. Everything else runs without one: human steps, scripts, triggers, the audit trail.

You do not need a Google Cloud project, a Firebase project, or a mail provider. Each is optional and the sections below say what you give up by skipping it.

This page is the path. Install Mediforce in the documentation is the reference beside it: every variable, which ones the server refuses to boot without, and what each one changes.

1

Get a server

Any Ubuntu host works. If you have no preference, Hetzner Cloud is what we run on and a CPX31 is comfortable for a team.

  1. Open console.hetzner.cloud and pick your project.
  2. Add Server → location close to your users.
  3. Image: Ubuntu 22.04. Type: CPX31 (4 vCPU, 8 GB).
  4. Add the SSH keys of everyone who will administer the box. Every key added here gets root access.
  5. Create it, and note the IP.
You can add keys later with ssh-copy-id, but adding them at creation is less fiddly than editing authorized_keys on a live box.
2

Point a domain at it

One A record from the name you want to the server's IP. At Cloudflare that is DNS → Add record → type A, name your subdomain, IPv4 the server IP.

Set the proxy to DNS only. An orange-cloud proxied record puts Cloudflare in front of port 80, and Caddy's certificate challenge never reaches your server, and the first boot then hangs without TLS. The same applies to any CDN.

DNS wants to be in place before the first deploy, because Caddy asks for the certificate as it starts. If you deploy first, it retries, so you are not stuck, just waiting.

3

Decide how people sign in

Email and password is on by default. If you set nothing at all, you get a working login and can invite people from inside the app. Everything below is optional on top of that.

GoogleSet GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET from a Google Cloud OAuth client. The redirect URI is https://your-domain/api/auth/callback/google, exactly, including the path.
Your own IdPOIDC_ISSUER, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET, for Keycloak, Entra or Okta. One per deployment.
Magic linksENABLE_MAGIC_LINK=true. Needs working email, below.
Turning on Google or OIDC makes ALLOWED_EMAIL_DOMAINS mandatory. Without it, any account at that identity provider could sign itself in, meaning any Google account on earth. The server refuses to boot in that state rather than serve it, and the error names the fix. Set it to your domain, for example ALLOWED_EMAIL_DOMAINS=acme.com.

Every variable behind these, and the invite and auto-join rules that go with them, are in Install → Sign-in.

The allowlist governs people signing themselves in. Anyone you deliberately invited can sign in whatever their email domain, which is what lets you bring in an external collaborator without listing their employer.

4

Decide about email

Optional. Mediforce degrades rather than breaks without it, and two things change: inviting someone still creates their account, but the app tells you "Email not sent, let them know to sign in" and you pass it on yourself; and the Send email step appears greyed out in the editor, because the instance will not offer what it cannot do.

To send mail, set EMAIL_PROVIDER to smtp or mailgun and fill that provider's group. To run with none, set MEDIFORCE_DISABLE_EMAIL=true. The server refuses to boot in the ambiguous middle, where email is on but nothing can send it. The SMTP_* and MAILGUN_* groups are listed in Install → Email.

5

Run the bootstrap

The repository carries an interactive bootstrap that takes a fresh Ubuntu box all the way to a running deployment. Run it from your laptop, because it drives the server over SSH.

# on your machine, not the server
git clone https://github.com/Appsilon/mediforce.git
cd mediforce
python3 scripts/bootstrap-server.py --host YOUR_SERVER_IP

It works through seventeen steps: system packages, Docker and its builder GC cap, a deploy user, the clone into /opt/mediforce, your API keys, the domain, sign-in, the env files, the Postgres data directory, the firewall, the first deploy, and a smoke test.

Two things make it pleasant to use. It detects before it asks, so anything already on the box is offered back rather than redone, and it saves its state in ~/.mediforce/, so a Ctrl-C or a dropped connection costs you nothing. Re-run the same command and it picks up where it stopped.

Deploying a private fork? Pass --repo Org/Name. The script generates a deploy key on the server, shows you the public half and waits while you add it under that repo's Settings → Deploy keys with read access.

Useful flags: --dry-run describes every action without making changes, --only-step docker_gc runs a single step, and --from-step N skips ahead.

6

Check it worked

ssh deploy@YOUR_SERVER_IP
cd /opt/mediforce
docker compose -f docker-compose.prod.yml ps

Everything should read running, except migrate, which should read exited (0), because it does its job once and stops. Then open your domain. With no workspace yet, Mediforce takes you straight to creating one.

Agent images keep building in the background after the app is up, so the first workflow run may wait on them. Follow along with tail -f /var/log/mediforce-deploy.log.

7

Keep it running

Images are tagged latest on GHCR, so an upgrade is a pull and a recreate. Migrations run again on the way up, and Install → Upgrading has the detail.

docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d

Back up Postgres before upgrading anything holding real work:

docker compose -f docker-compose.prod.yml exec postgres \
  pg_dump -U mediforce mediforce > mediforce-backup.sql
Keep SECRETS_ENCRYPTION_KEY somewhere else. It encrypts every workflow secret at rest. Lose it and they are unrecoverable: a database backup alone will not bring them back. Store it off the machine running Mediforce.

Doing it by hand

If you already have Docker hosts, a reverse proxy and a deployment pipeline, skip the bootstrap. It is a convenience, not a requirement. The deployment is an ordinary Compose stack:

git clone https://github.com/Appsilon/mediforce.git
cd mediforce
cp .env.example .env
# fill in .env, then
docker compose -f docker-compose.prod.yml up -d

Every variable, which ones the server refuses to boot without, and what each one changes is in Install Mediforce, the reference that ships with the code and the one to trust if this page and it ever disagree.

If you get stuck

Ask in Discord or open an issue on GitHub. Deployment problems are usually DNS, a proxied record, or a missing ALLOWED_EMAIL_DOMAINS, and the server's boot error names which.
