## [2026-08-30]

### Fixed
- `MEDIFORCE_ATTACHMENT_MAX_BYTES` now reaches the process that reads it. The knob was documented in `.env.example` and honoured by [`_limits.ts`](packages/platform-api/src/handlers/tasks/attachments/_limits.ts), but [`docker-compose.prod.yml`](docker-compose.prod.yml) never forwarded it to `platform-ui` — the service hosting the upload handler — so lowering the attachment ceiling on a deployment silently did nothing and every upload kept the 100 MiB default. Forwarded as `${MEDIFORCE_ATTACHMENT_MAX_BYTES:-}`, which staging inherits through its overlay; unset still means the default, since the resolver treats an empty value as absent.
- Every CLI example in the docs site now runs. `website/docs/` had drifted to a positional argument style the CLI does not accept — `run start my-workflow`, `workflow register ./f.wd.json`, `secret set KEY` — and [`define-command.ts`](packages/cli/src/define-command.ts) rejects extra positionals outright, so each of those 16 examples exited 2 with "Unexpected positional arguments" rather than doing anything. The real shapes are `--workflow`, `--file` and `--key`; the `namespace` family takes `--handle`, not `--namespace`; `workflow copy` needs `--target-namespace` and `workflow import` needs `--path`; `assistant ask` takes `--definition`, not `--canvas`; `task complete` takes `--payload '{"kind":"verdict","verdict":"approve"}'`, not `--verdict`. Three CLI-reference rows named commands that do not exist: `workflow trigger <name>` (it is eight subcommands — `trigger-list|add|update|start|stop|remove|export|import`), `run bulk` (`run bulk-cancel` / `run bulk-archive`), and `model validate <workflow>`, which in fact takes comma-separated **model IDs** and never sees a workflow. `agent get`/`set-visibility` address an agent by ID, not name; `system credits` requires `--namespace`; and `--namespace` on the listing commands was documented as scoping a result it is not even read for, since `workflow list` and `agent list` take no arguments and return everything the key can see. `system images` / `rmi` / `disk` were missing from the reference. Two claims contradicted [`docs/`](docs/guides/verify-a-workflow.md) and the source: a Dry Run's `spawn` action was described as starting **real** runs on three pages, where [`spawn.ts`](packages/core-actions/src/handlers/spawn.ts) propagates `dryRun` to every child — it is the one action that knows about dry runs — and the step-type tables listed three of the four types, omitting `review` (the enum is `creation | review | decision | terminal`). The cron section also now states the constraint [`cron-utils.ts`](packages/workflow-engine/src/triggers/cron-utils.ts) enforces at save: five fields, UTC, minutes on the quarter hour, so `*/5 * * * *` is refused rather than silently firing a third as often as asked.
- `pnpm check:docs` passes on the docs site instead of failing it. [`check_doc_links.py`](scripts/check_doc_links.py) called seven links broken that Docusaurus resolves correctly — an extensionless target (`../run/verify`) is a live link under `website/` and a dead one everywhere else, because GitHub renders the rest of the repo and does not fill in the extension — so it now resolves `.md`, `.mdx` and `/index.md` under `website/` only. Its `SKIP_DIRS` name match also hid a page from every check: `build` names generated output, but it is equally a docs section (`website/docs/build/`), so the name now only counts until the first `docs/` segment. That page's links had never been checked.
- `prod.mediforce.ai` no longer 525s at Cloudflare: Caddy now auto-provisions TLS certs and proxies for an optional `DOMAIN_ALIASES` list alongside the primary `DOMAIN`, so the new production hostname works while `phuse.mediforce.ai` keeps serving for backward compatibility [#1198](https://github.com/Appsilon/mediforce/pull/1198).
- Google SSO no longer bounces sign-in from `prod.mediforce.ai` over to `phuse.mediforce.ai`: `AUTH_URL`, `NEXT_PUBLIC_APP_URL`, and `DOMAIN`/`DOMAIN_ALIASES` on the prod server were still pinned to `phuse.mediforce.ai`, so the OAuth `redirect_uri` and the CSRF cookie's host disagreed whenever a login started on `prod.mediforce.ai`. Repinned to `prod.mediforce.ai` as canonical on the server, and `.env.example` now documents the requirement so the next multi-domain setup doesn't repeat it [#1198](https://github.com/Appsilon/mediforce/pull/1198).
- The save-version and "Before you start" dialogs no longer open with a four-rung diagram of the verification pipeline above the thing you came to do. Naming a version and reviewing what is actually missing are the decisions on those screens; the ladder restated platform vocabulary every time either dialog opened, pushing the version field and the warnings down the modal. The pipeline stays documented in [`docs/guides/verify-a-workflow.md`](docs/guides/verify-a-workflow.md), and the honest "some checks could not run" signal survives as one sentence in the readiness summary rather than a rung state — on every variant of that dialog, including a run that asks for trigger input. A "How verification works" link keeps the guide one click away, which was the only part of the ladder a user could act on [#1233](https://github.com/Appsilon/mediforce/issues/1233).
- Creating a workflow saves it into the workspace you are in, on all three save buttons. The namespace picker defaulted to the first workspace you belong to — usually your personal one — so a workflow started from an organisation workspace was written there while the redirect looked for it here, reporting "Workflow definition 'x' v2 not found" and "Item unavailable". **Save**, **Save & Dry Run** and **Save & Start Run** now all follow the workspace the save actually targeted: the redirect goes where it saved, and the run starts where the version exists rather than in the workspace named in the URL. The picker also stops displaying a workspace it would not write to — a route handle you are not a member of, or the moment before your workspaces have loaded. The dead `yaml-editor.tsx`, carrying the same first-workspace default with no consumers, is deleted [#1234](https://github.com/Appsilon/mediforce/issues/1234).

### Added
- The product documentation site now has somewhere to live: **mediforce.ai/docs**, published by [`pages.yml`](.github/workflows/pages.yml). mediforce.ai turned out not to be in the CI pipeline at all — it is GitHub Pages' *legacy* builder serving `main:/docs`, which GitHub rebuilds itself on every push, so nothing in this repository built or published [`website/`](website/). A `docs.` subdomain was not available without a second host: a repository gets one Pages site and mediforce.ai holds it. The docs mount on a path instead, and one workflow composes both halves into a single artifact — Jekyll builds `docs/` to the site root, the Docusaurus build is copied in at `/docs`. That Jekyll step is load-bearing: every `.md` under `docs/` is rendered and already live on the public internet (`docs/README.md` serves as `mediforce.ai/README`, ADRs and guides alongside it), so publishing the folder as plain static files would have kept the `.html` pages and 404'd every Markdown one. Pull requests build the artifact without deploying it, which is also the only thing in CI that builds *or* type-checks this package — the root `tsc -b` has no `website` reference and `docusaurus build` transpiles without checking types, so the docs build was gated by nothing and a broken one would have surfaced at deploy. The trade for staying on one host is no PR preview URLs and a shared deploy, so a broken docs build blocks a marketing-site fix. Serving it requires one manual step after merge, **Settings → Pages → Source → GitHub Actions**, kept last so the live site is never in a gap [#1265](https://github.com/Appsilon/mediforce/pull/1265).
- [ADR-0019](docs/adr/0019-workspace-scoped-roles.md) (**proposed**) puts the role model up for decision before any of it is built: a process role (`reviewer`, `PI`, `approver`) would be held **inside one Workspace**, not across the Deployment. On acceptance it partially supersedes [ADR-0002](docs/adr/0002-firebase-auth-to-nextauth.md) §5, which chose a global `user_roles` table to protect namespace-blind notification targeting and left the door open for "per-workspace functional roles ... later as a real product decision if asked". The migration backfills each existing global row across that user's memberships, which would keep every notification a role holder gets for workspaces they belong to and deliberately drop the ones for workspaces they do not — a §12 regression accepted in the ADR rather than found later. Recorded against three verified facts about today's code: nothing writes `user_roles` (the invite service can, but its only caller hardcodes an empty list), nothing reads `step.allowedRoles` *for authorization* (the engine's `RbacService` call sits behind a constructor slot production passes `undefined` into), and the Human actions inbox already pivots on `session.user.roles[0]` — a namespace-free value that hides a second role's queue [#1247](https://github.com/Appsilon/mediforce/issues/1247).
- Process roles can be granted, for the first time. `user_roles` was written only by the one-time `seed-user-roles` migration and by `PostgresInviteService.seedInvite`, whose one caller hardcoded `roles: []` — so every `allowedRoles` in the 23 workflow definitions here named people who could not exist. Migration `0042` scopes the table per [ADR-0019](docs/adr/0019-workspace-scoped-roles.md): `namespace` (FK to `workspaces.handle`, cascade) plus a nullable `workflow_name` where `NULL` means every workflow in the workspace, keyed `UNIQUE NULLS NOT DISTINCT` because a primary key cannot span a nullable column. Owner/admin set a member's roles with `mediforce namespace set-member-roles <handle> <uid> --roles reviewer,approver [--workflow tealflow]` or `PUT /api/namespaces/:handle/members/:uid/roles` (full replace — the array is the end state, `[]` clears), and `listNamespaceMembers` returns `roles` per member for **every** member, not only managers: a member has to be able to see who the reviewer is. `mediforce namespace list-members <handle>` prints that roster with the two columns labelled apart (MEMBERSHIP vs PROCESS ROLES), so a grant can be read back from the same surface that made it instead of only in SQL. Note the plural — `set-member-role` (singular) is still Membership (`owner|admin|member`), the distinction `CONTEXT.md` draws, now restated in both commands' help text. Two things the ADR flagged as silent when wrong are handled rather than deferred: notification targeting moved from the deployment-wide `getUsersByRole(role)` to `getUsersByRoleInNamespace(role, namespace, workflowName)`, so a grant narrowed to workflow A no longer emails its holder about runs of workflow B, and leaving or being removed from a workspace deletes that user's grants there in the same transaction as the membership row (the `namespace` FK cascades on workspace *deletion*, a different event) — without it, re-adding someone six months later silently restores a role nobody granted. Deleting a workflow drops the grants narrowed to it for the same reason, and so does transferring one to another workspace — the source name comes free either way, and the grants do not travel with the workflow because their holders need not be members of the destination. The membership check is the write's own, not the handler's: `setRolesForUser` takes the member's `workspace_members` row `FOR UPDATE` before replacing anything, so a removal committing mid-request cannot recreate the grant the cascade just deleted, and two admins editing the same member serialize instead of both deleting the set they read and inserting their own — which under READ COMMITTED leaves the union, a set neither of them asked for. The migration backfills each global row across its holder's memberships, which keeps every notification a role holder gets today for workspaces they belong to and drops the ones for workspaces they do not — the §12 regression ADR-0019 accepted deliberately — and then seeds every role a live workflow definition declares to that workspace's owner and admins, recorded as a `namespace.member_roles_seeded` audit event, so the gate #1249 adds does not land on an empty table and strand every declared step (AGENTS.md §13). `CallerIdentity` carries `namespaceProcessRoles` (workspace-wide grants only; a narrowed one needs the workflow in hand, which only the handler has) so that gate costs no second round-trip. `session.user.roles` stays a flat array and is now a cross-workspace union — the shape change belongs to the inbox that consumes it, [#1251](https://github.com/Appsilon/mediforce/issues/1251) [#1248](https://github.com/Appsilon/mediforce/issues/1248).
- Creating a workflow now states the four ways to author one, a reason to pick each, and how to start it — without a checkout. A **Ways to author** popover in the Workflow Designer toolbar (so it appears once you are actually creating something, not in the catalog header) names blocks on the canvas, the AI Assistant, import from git and the `/design-workflow` agent skill. The two paths that live outside the browser were previously undiscoverable from the product: the only in-app statement of authoring paths was a hover tooltip on **Workflow source code** listing three canvas-local ways with no reason attached, and that list is replaced by the popover it duplicated. Each entry carries its first move rather than its name alone — the skill entry gives the `git clone`, the agent to open the checkout in, and the `/design-workflow` invocation, since a skill you cannot reach is the same dead end as one you were never told about. The import entry is a click, not an instruction: it navigates to the workspace home with the importer already open, via a new `?import=source` parameter, because the dialog does not live on the editor page. Its footer opens the full guide on GitHub — a third `docs-links.ts` constant next to the Docker-setup and verification ones — instead of printing a repo-relative path only a reader with a checkout could follow. The AI Assistant's empty pane also points at `/design-workflow` for the case it cannot serve — a package with code in it, not just steps. Wording is condensed from [`docs/guides/create-workflow.md`](docs/guides/create-workflow.md) § "Pick an authoring path" into [`authoring-paths.ts`](packages/platform-ui/src/lib/authoring-paths.ts), and the guide records the pairing [#1185](https://github.com/Appsilon/mediforce/issues/1185).
- Every `packages/*/` and `apps/*/` directory now carries a `README.md` — 21 were missing, only `platform-ui` and four apps had one. [`docs/README.md`](docs/README.md) records the convention that produced them: a package or app documents itself, `docs/` covers only what spans more than one package, and a new package ships its README in the same PR. This closes the gap [ADR-0017](docs/adr/0017-retire-llm-maintained-wiki.md) accepted when the wiki was retired — "what is `packages/agent-runtime` for?" had been answerable only from the one-line `<stack>` block in `AGENTS.md`. Thirteen archived wiki entity pages seeded the new files and were verified against the code first, which is where most of the work went: `platform-infra`'s page described Firestore repositories, Firebase auth and a `firebase-admin` dependency for a package that now has none of them (drizzle + `postgres`), `workflow-engine` still listed `TriggerHandler` and `src/graph/` (now `WebhookRouter`, and graph validation moved to `platform-core`), the plugin pages named `platform-ui` as the registration site after the composition root moved to `platform-api/src/services/platform-services.ts`, `MockClaudeCodeAgentPlugin` had been renamed `MockAgentPlugin`, and `cowork-workflow-designer.wd.json` no longer exists. The four surviving plugin pages collapsed into one [`packages/agent-runtime/src/plugins/README.md`](packages/agent-runtime/src/plugins/README.md), since they describe single files in a shared directory rather than packages. Ported pages are deleted from `docs/archive/knowledge-base/`, so no second copy can disagree; the five `supply-intelligence` pages stay, describing deleted code, as the record of the drift ADR-0017 diagnosed. READMEs carry no frontmatter, matching the five that already existed — the `status`/`audience`/`last_reviewed` header stays scoped to `docs/`, and a colocated README's freshness comes from `git rm` carrying it off with the code instead ([PLAN-0017](docs/archive/PLAN-0017.md)). The convention is enforced rather than trusted: new `pnpm check:readmes` ([`scripts/check_readme_coverage.py`](scripts/check_readme_coverage.py)) fails the build when a package or app has none, and it runs in [`ci.yml`](.github/workflows/ci.yml) rather than the docs workflow because a new package containing no Markdown file matches no `**.md` path filter — the exact case it exists to catch. `AGENTS.md` gains rule 11, "sync the docs the change invalidates": the diff that renames a symbol fixes the README naming it, in that diff, never as a follow-up issue — colocation decides *which* README (touched `packages/foo/src/` → `packages/foo/README.md`), which is the routing the wiki never had. The pre-existing duplicate `10.` in the rules list is renumbered.
- The four checks that answer "will this workflow work?" — schema validation (runs on every save) → **Workflow readiness check** (image, secrets, model, credits) → **Dry Run** (agent and script work mocked) → **Run** (the only one that answers behaviour) — are documented in one place, the new guide [`docs/guides/verify-a-workflow.md`](docs/guides/verify-a-workflow.md), linked from `workflow validate` on success, which now says which gate it is and what to do next. The "Before you start" dialog reports "some checks could not run" rather than a clean bill of health when a probe it needed never completed — an unreachable image registry, a failed credits probe or a model-registry lookup that errored produce no warnings, exactly like a pass. CLI help stops contradicting the pinned terminology: `run start --dry-run` described itself as "real execution, labelled for testing" when it in fact mocks every agent and script step, and `workflow register --dry-run` now says outright that it is schema validation and executes nothing. The guide and the CLI help both state the trap the old copy left implicit: a Dry Run is **not** a sandbox — only `agent` and `script` steps are mocked, so an `email` action still sends the mail and an `http` action still hits the real endpoint. The guide also stops claiming the readiness check gates every start; it runs in the app, and `mediforce run start` and `POST /api/runs` skip it [#1188](https://github.com/Appsilon/mediforce/issues/1188).
- The Agents, Tools and Tool catalog surfaces now say what the concept is before asking anyone to configure one, so the definitions in [`CONTEXT.md`](CONTEXT.md) finally reach the user rather than living only in the repo. The Agents, Tools and Tool catalog pages carry it in a `ConceptPopover` beside the page title — a labelled info trigger rather than a hover tooltip, so the text is reachable by click, keyboard and touch, matching the popover [#1185](https://github.com/Appsilon/mediforce/issues/1185) introduced for the same reason; the agent create and configure forms, which have no title to anchor a trigger to, keep it inline as a `ConceptIntro` box standing in for a page header. An **Agent** is a reusable configuration a workflow step calls by id — system prompt plus MCP server bindings — unversioned, so editing one changes every step already referencing it; a **tool** is an MCP server, split into stdio entries an admin curates in the catalog and agents reference by id, and HTTP endpoints any member binds to an agent, with a step able to narrow that set but never widen it; a **catalog entry** is an admin-approved stdio server whose command lives in the catalog rather than in the agent, which is what keeps arbitrary commands out of agent configuration. The copy is deliberately silent about behaviour the runtime does not have, and says so where the form implies otherwise: the **Foundation model** picker on both agent forms now carries "recorded on the agent for reference — a run takes its model from the workflow step that calls the agent", because no runtime path reads the agent's `foundationModel` (`resolveAgentIdentity` passes only `systemPrompt` through as `agentIdentityPrompt`; the model comes from `step.agent.model`). That divergence, and the absence of any `skills` field on the Agent schema, are now recorded in `CONTEXT.md` § **Agent** — the issue assumed they already were — and two stale comments in `agent-runtime` claiming skills arrive from the AgentDefinition are corrected. Adding the callout surfaced a duplicate the page already had: an empty Tool catalog rendered "No catalog entries yet." twice side by side — once from the entry list and once from the editor pane — so the editor pane now says what it actually means ("Nothing to edit yet.") and the list drops the "enable stdio MCP servers for agents" gloss the callout above it now carries. The Tools page's **Add HTTP binding** button stops promising an action it cannot perform: an HTTP binding is a key in the agent's `mcpServers` map, with no namespace-level store to create one in, so the button was always a hop to the agents list — it is now labelled **Bind to an agent** and styled like the other navigation links rather than as the page's primary action. Creating an agent now lands on that agent's Configure page rather than back on the catalog: MCP servers can only be bound once the agent is persisted (the binding form's `agentId` is needed for the OAuth connect flow, whose tokens are stored per-agent per-server), so creation continues into the page that owns them instead of dead-ending on a grid of cards. Binding at create time is possible — `CreateAgentInputSchema` already accepts `mcpServers` — and is tracked as [#1262](https://github.com/Appsilon/mediforce/issues/1262) [#1187](https://github.com/Appsilon/mediforce/issues/1187).
